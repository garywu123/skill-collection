## 3. Ownership and role sequence

### 3.1 Artifact ownership

|---|---|---|

| Functional Spec, optional at scale | `functional-spec` | Observable functional and relevant quality requirements |
| Architecture Design | new `architecture-design` | Components, contracts, deployment, data ownership and technical decisions |
| Roadmap / Feature Map | `feature-map` | Outcomes, dependencies, sequence and existing Feature statuses |
| Code Style | `code-style` | Scoped code structure, expression, comments and documentation |
| Testing Strategy | new `testing-strategy` | Reusable risks, data, oracles, measurement methods and independent-test triggers |
| Storyboard | `feature-storyboard` | States/transitions for early product questions or Features |
| Feature / validation Plan | `feature-plan` | Outcome, constraints, segments, specific test scenarios, handoff and actual results |
| Implementation and initial tests | `feature-delivery`, Producer | Incremental TDD, production code, executable self-tests |
| Supplemental tests/fixtures and evidence | Tester assignment under the reviewed Plan/strategy | Independent execution after Producer readiness; no new Tester Skill required |
| Root/nested instructions | `coding-agent-instructions` | Routes, verified commands and meaningful scoped operating differences |
| Settings and run evidence | Cross-agent | Effective roles, per-run limits, snapshots, decisions and results |

Use existing canonical paths. New-project defaults are `docs/architecture.md` and `docs/testing.md`; adopt existing General Design content rather than duplicate it. Use `<subproject>/docs/code-style.md` for real scoped differences, or one language-sectioned file for a small project. Shared rules have one owner.

Keep Feature Plans in `docs/features/`; standalone validation can use `docs/plans/<topic>.md` without a fictional Feature ID. Runtime logs stay outside product documents.

### 3.2 Roles and Skills

Producer authors artifacts using the assigned Skill. Architecture, Code Style and Testing Strategy are specialties, not mandatory separate agents. Reviewer loads that Skill's relevant review criteria and project contracts, returns findings, and leaves writing to the owner. Review mode must not trigger the Skill's authoring procedure. PM dispatches, adjudicates and reports without redoing every specialist analysis.

Retain the `cross-agent` public entry/CLI, described as bounded project orchestration supporting single-provider, multi-session and cross-provider work. A/B cross-provider review is one execution choice, not the entire purpose. A second PM Skill or manager hierarchy is unnecessary for this release.

One session may handle compatible production specialties; a role may span sessions. Independent Tester/Reviewer work on an artifact needs a distinct session, not a role switch inside its Producer transcript. Retain existing fresh stage sessions where applicable; bundle related document work only where a bounded current stage supports it. Logical review points do not mandate permanent teams.

### 3.3 Default flow

```text
Producer: Architecture -> scoped Code Style / initial Testing Strategy
Reviewer: relevant design and policy artifacts
Producer: Feature Map -> Reviewer: Map
Producer: Feature Plan, including test design -> Reviewer: Plan
Producer: Delivery, implementation + TDD + self-tests
Optional Tester: derive scenarios -> inspect implementation/tests -> supplement and execute
If needed: PM adjudication -> Producer repair -> affected verification
Reviewer: final implementation, all test changes and current evidence
PM: adjudication and completion report
```

This is a dependency outline, not a demand to regenerate every document. Brief/Spec and early Storyboard inform design when applicable; refine initial strategy using Map scope before detailed planning. Reuse valid artifacts.

Plan Reviewer is ordinary Reviewer work: check scenario coverage, realistic data, acceptance decisions and feasibility; return findings for Producer to revise the same Plan. It normally writes neither test code nor a separate assessment document. First release has no separate Tester plan-assessment call.

## 4. Track A: lifecycle contracts

### 4.1 Product discovery and early visualization

Allow Brief/Spec review against the user's authorized interview evidence, not only the finished draft. Distinguish the user's statements from model suggestions, confirmed decisions from candidates, and current decisions from superseded statements. Preserve source locations or short exact quotations when available; never invent a transcript or source locator.

Do not copy a full transcript into every worker prompt. Use relevant notes and retrieve original passages for disputed or high-impact claims. A summary written by the Producer is not the sole independent evidence of user intent. Save notes only when requested or included in an authorized discovery workflow; retain the existing ability to explore without writing files. Do not bulk-import sensitive conversation content into version control.

Extend Storyboard inputs to accept a Brief, a Spec section, or an explicit product question before Feature mapping. Use a stable topic slug without a fake Feature ID, preserve state/transition IDs, and link the same artifact later. Mark candidate behavior as unresolved where appropriate. A sketch does not confirm a requirement. Retain low fidelity, browser verification, and the boundary against implementing real application logic.

Keep Functional Spec optional for a small project. Choose document scale because requirements need organization, not because a table crosses an arbitrary line count.

### 4.2 Architecture Design

Create `architecture-design` with explore, write/update, and review/audit behavior. It owns durable cross-feature design and can be invoked independently. Read the Brief, requirements, existing designs, relevant code/configuration, and authorized domain sources. Do not invent missing business requirements.

Cover only decisions needed by the project: application form, frontend/backend/library/service boundaries, contracts, data ownership, dependency direction, deployment assumptions, architectural dependencies, and relevant quality constraints. Language or subsystem boundaries alone do not justify microservices or separate documents. Preserve sound existing choices.

Express material constraints as subject, operating conditions, required property/budget, source, and verification reference. Product-level memory, latency, capacity or reliability requirements stay with the product requirement owner; Architecture translates them into technical decisions or budget allocation. Testing owns how they are measured. Do not invent a universal memory ceiling.

When feasibility is uncertain, identify a bounded validation question and request a validation Plan through the PM. Architecture consumes the evidence and records the resulting decision. It does not create an independent experiment-planning framework.

### 4.3 Testing Strategy and business-risk exploration

Create `testing-strategy` to establish, review and update reusable project testing rules. Its output is a concise strategy with executable entry points where verified, not an inventory of all future cases or a report of fictional test success. Add scoped references only when the project needs substantial distinct guidance.

Include applicable business invariants and source references; unit/integration/end-to-end boundaries; fixture provenance and scale; mock limits; test discovery and skip behavior; environment/isolation requirements; resource measurements; regression triggers; and independent-Tester triggers. Identify production and test projects explicitly. Use separate test projects when appropriate to the actual stack, such as .NET test `.csproj` files, without imposing one project per test category everywhere.

For algorithm work, specify the correctness oracle: known answers, an independent small reference implementation, justified properties, or other evidence independent of simply repeating the implementation. Where relevant, define seeds, tolerances, baseline comparisons and scale profiles. Line coverage and green exit codes do not establish behavioral coverage or assertion strength.

Feature planning must read the strategy and derive risks from actual users, workloads, data, failure consequences, and changed boundaries. First inspect available project evidence, then ask a small number of high-value questions that explain why the answer changes design or acceptance. Search industry information only for relevant uncertainty; cite primary sources and distinguish applicability from speculation. Do not turn external advice into a mandatory project rule without authority.

For a data-loading Feature, useful questions may include representative/worst supported dataset size, simultaneous old/new data residency, cancellation, repeated runs, peak versus steady memory, target hardware, acceptable response time and recovery. These are examples to select from, not a mandatory checklist for every Feature.

Promote a discovery into the project strategy only when it is reusable and supported. A missed case under an existing requirement can be added to the current Plan/test suite. A new business rule or resource budget first needs a decision by its owning source. Do not automatically learn every incident into permanent policy or silently expand scope.

### 4.4 Feature Map and Feature Plan

Remove shared architectural authorship from `feature-map`; route to Architecture. Retain vertical outcome-based slicing across frontend/backend/algorithm components. Domain-oriented knowledge does not require domain-first delivery. Internal DTOs, routes or layer setup are not automatically separate Features.

Remove the Plan's hard 60-line limit and all duplicate instructions/templates enforcing it. Review the Map's 60-line/about-eight-row triggers and other fixed limits as readability signals, not automatic reasons to create a larger document hierarchy. Do not weaken concision into unlimited prose: delete repeated upstream content, empty template sections and speculative implementation inventories.

Keep one Plan per independently useful Feature outcome. If a proposed Feature contains multiple independent outcomes, return a scoped replanning request to the PM. The PM can dispatch Map revision and Plan continuation within an already-authorized objective; it must not invent product scope. Long execution alone calls for segments, not new Features.

Each substantial segment names its outcome, owned areas, prerequisites/contracts, applicable constraints, focused checks, handoff and remaining integration. Choose checkpoints at verifiable boundaries with context/time allowance. Do not create one Plan file per checkpoint or a compulsory Delivery Plan layer. Extract substantial segment detail only when it improves navigation and ownership; preserve one canonical acceptance/status location.

The Plan begins with a short current execution position: valid source links, completed/next segment, remaining checks and material blockers. Preserve key decisions with reasons; keep transcripts and routine activity logs in runtime evidence. A fresh executor must recover without the prior chat, using the Plan plus explicit repository references.

Add an explicit standalone validation mode to `feature-plan`. It accepts a bounded question without requiring a Brief, Map or fictional Feature. Specify hypothesis/question, inputs and representative data, comparison/oracle, procedures, metrics, budget, stop conditions, evidence and decision criteria. Keep experiment execution completion separate from `supported`, `not supported`, or `inconclusive` conclusions. Negative findings may complete an experiment; they do not verify a product Feature. If the planned evidence is missing, report incomplete validation.

`feature-delivery` must recognize this mode and execute its bounded experiment without inventing a Map status. Ordinary Feature behavior and guided/auto delivery remain supported.

### 4.5 Delivery, tests and change requests

Keep Producer-owned incremental TDD: for a behavior, create/update a focused test, observe its intended failure when practical, implement, and verify. Do not require all tests to be written and frozen before any implementation. Confirm assertions match expected behavior and tests are actually discovered/executed.

Require reviewable test and runner changes. B1 supplies a change summary; A remains usable through ordinary diffs and actual results before B1 exists. B3 protects Tester-owned tests specifically, while Producer retains incremental TDD ownership of its own tests.

Where independent testing or review is selected, Producer completion is readiness for that gate, not final Feature acceptance. Keep the Feature `in_progress` until all selected mandatory checks, Tester work and required review are complete against the final relevant revision. Allocate the final Plan/Map status write to the Producer or a narrowly scoped finalization step; Reviewer remains read-only. Standalone delivery without independent review can retain its existing completion path.

Use existing Map/Plan ownership for refactors and changes. Reopen the same Feature for the same user outcome; add a Feature only for a new independent outcome. Update the authoritative requirement/design first, then affected Storyboards, Maps and Plans; reset only invalidated evidence. Record a short reason and impact in the existing Plan. Link an external change-request record when the organization requires it, without creating a parallel CR Skill or mandatory document.

An authorized PM may coordinate upstream changes instead of requiring the user to invoke every Skill. Ask only for unresolved choices that materially affect product behavior, accepted constraints, permissions, cost commitments, or the user's explicit gate. Agents must not rewrite authoritative inputs to hide a failed test.

### 4.6 Code Style and instruction maintenance

Extend `code-style` with explicit define, audit and apply operations. Preserve compatibility for current write/audit intent. Define creates rules; audit reports scoped deviations; apply edits only the authorized code scope under already-established rules. Do not adjust the rule document to excuse existing violations. Formatter/linter commands remain the preferred way to apply deterministic rules; introducing or changing tool configuration requires scope that includes it.

Move architectural dependency and system-boundary decisions to Architecture. Keep code-expression, file organization, comment intent and API documentation rules with Code Style. Applying comments or restructuring code can affect semantics; it is not automatically a judgment-free task. Protect public behavior and inspect the diff, then run relevant checks.

Support scoped style documents and nested `AGENTS.md` only for actual local differences. Root guidance routes to applicable files rather than repeating them. Do not create empty instruction files for every folder or duplicate shared rules in every language project.

After changes to architecture, test strategy, commands, project structure or instruction routes, require an instruction-impact assessment: updated with verified evidence, assessed with no change needed, or unresolved. The requirement is to assess, not to touch `AGENTS.md` after every Feature. Use `coding-agent-instructions` for substantive instruction changes; preserve Code Style's narrow authority to update its own route. A low-cost worker may synchronize verified routes/commands but must escalate new semantic policies.

## 5. Track B: serial increments

### 5.1 B1: test-change summary

Generate a deterministic, revision-specific summary from existing snapshots and configured test routes. Include changed test paths and relevant hunks; supported-framework skip/disable markers; runner/filter/config changes; and fixture/mock changes. Preserve source locations and mark unsupported classification unknown. An empty detected summary proves neither unchanged tests nor adequate coverage.

Assertion/expected-value changes are optional where reliable existing parsing supports them; raw hunks are acceptable. Counts are signals, not quality scores. Initial loose tests can remain unchanged, so Reviewer still assesses requirements and assertion strength. Preserve incremental TDD rather than freezing all Producer tests.

Provide executed/failed/skipped counts only from an existing supported structured report, such as JUnit XML or TRX. Record freshness, command, test scope and handling of retries/duplicates. Otherwise show unknown with command/exit evidence; avoid cross-framework console parsing and whole-repository claims from one project's report.

Supply this summary as fixed Reviewer input on each reviewed revision. B3 adds separate attribution for Producer changes to Tester-owned artifacts. B1 needs no Tester implementation.

### 5.2 B2: direct stage roles

Extend `[stages.<stage>]` with `producer` / `reviewer` values in the existing `provider:model:effort` format; B3 adds `tester` when selected. Resolve explicit authorized override, stage role, then explicit role default. Display the effective choice and fail clearly on missing/unsupported configuration.

Design, delivery and mechanical application can choose different models/effort without logical profiles. Use a bounded explicit override when an operation needs different settings; avoid a stage-operation-profile hierarchy. Exact models come from available authorized clients at configuration time, not every Skill. Worker settings cannot change the model of the already-open PM.

Preserve explicit executable paths and legacy defaults. Define compatible saved-run behavior before changing parsing/state. Dispatch applicable lifecycle Skills without bypassing their contracts, including when a current bounded `general` stage is used. B2 can ship independently of B1.

### 5.3 B3: selection and ordered execution

B3 requires B1/B2 acceptance plus a recorded independent-verification use case from M0 or a bounded fixture. Testing Strategy remains useful without B3.

PM applies this order: explicit user/project requirement selects Tester; otherwise a reviewed Plan selects it for a concrete verification gap under applicable project risk rules; otherwise omit with a reason. New implementation evidence can reopen the decision within scope/budget. Producer proposes applicability, Plan Reviewer checks it, and PM follows that decision.

Examples include independent algorithm correctness checks, realistic-scale resource behavior, migration/recovery and cross-component state. Name the actual task instead of selecting Tester merely because work is complex. An unavailable required Tester leaves verification incomplete.

Tester runs serially after implementation and self-tests are ready, not continuously during TDD. Initial input supplies requirements/Plan/strategy routes before implementation diffs. In one assignment, it first derives a short candidate scenario list, then reads relevant implementation/tests to identify coverage gaps, then writes necessary tests/fixtures/scripts and executes them. Expand inspection as needed rather than auditing all project code. Keep the list in its result; no extra session or document is required.

| Discovery | Action and owner |
|---|---|
| Existing requirement lacks verification | Tester writes supplemental tests and executes; Producer reconciles Plan evidence as needed |
| Test exposes a production defect | Tester supplies reproduction; PM adjudicates; Producer repairs |
| Reusable testing lesson | Tester proposes; Producer updates Testing Strategy through its owning Skill when justified |
| Missing/new requirement or acceptance threshold | PM checks existing decisions, asks only for a material unresolved choice; Producer updates authoritative inputs before dependent acceptance |
| Tester test is incorrect | Record evidence and correct within authorized ownership and remaining Tester allowance, then rerun |

Industry experience informs hypotheses, not automatic requirements. An observed 2 GB peak without an agreed budget is a measurement plus an undefined criterion. Distinguish actual failure, coverage gap, inability to run and missing criteria. Tester authors supplemental executable checks itself; normative architecture/strategy/Plan changes remain Producer work.

### 5.4 B3: test protection and permissions

Save the paths and snapshot/content baseline of tests/fixtures added or modified by Tester, including existing test files it changes. Producer preserves these artifacts during repair. If a test seems wrong, Producer proposes evidence and a specific change; PM adjudicates before granting an exception. Unresolved material product choices still belong to the user.

After every Producer repair, detect and separately label changes to Tester-owned artifacts, including authorization and reason. Also surface shared-fixture, runner/config and filter changes that can bypass them. Authorized changes invalidate affected results; unauthorized changes fail the guard despite green tests. Producer's own TDD tests are not blanket-frozen.

Assign Tester test/fixture/script paths and declared generated/build/report outputs, excluding production fixes. Reuse supported provider restrictions and validate changes after execution. Post-run guards are detection, not preventive permissions. Account for tracked, new and relevant ignored outputs, report remaining limits, and preserve evidence instead of blindly reverting the user's tree. When prevention is required, use supported restrictions/disposable isolation or report that mode unsupported.

### 5.5 B3: budgets, repair and final review

Tester has at most one initial model invocation and one follow-up/retest invocation per delivery run. Failures and resumptions consume that allowance; a preflight failure before launching a worker is distinguished from a spent attempt. One call may run multiple bounded test commands. Deterministic reruns are not extra Tester model calls.

Producer repairs accepted Tester and Reviewer findings from one shared repair allowance, with no Tester-specific repair pool. Current repairs are coupled to Reviewer rounds: introduce only the compatible per-run state needed to track actual Reviewer counts separately from repair consumption. Specify the effective repair limit before launch, defaulting compatibly with current `max_reviews`. Preserve no-Tester behavior and document interactions with existing recovery.

For the new Tester path, count dispatched repair attempts including failed/resumed attempts without silently replenishing allowance. Track initial/retest use and shared repair use in existing state/history across resume, park and restart. Tester calls never increment `reviews_done`. This bookkeeping is required to enforce limits; it is not the deferred parent-budget system. Exhaustion means incomplete work, not a hidden retry, new-run reset or extra finalizer repair.

Final Reviewer examines Producer implementation/tests, Tester tests/fixtures, approved policy changes, summaries and evidence on the final relevant revision. It can challenge either team's work and perform permitted targeted checks, without repeating the entire test exploration. Accepted findings use the shared repair allowance.

After later edits, rerun affected commands. If new independent Tester judgment is necessary after its allowance is exhausted, report incomplete verification. All selected mandatory gates must pass before the writable owner/finalization step sets Feature status. A status-only finalizer is not an extra repair opportunity. Keep `completed-by-orchestrator` distinct from an independent pass, and experiment completion distinct from its supported/not-supported/inconclusive conclusion.
